# CHANGELOG — PiCar-Pro Merged Edition v1.0.0

## MOD v1.6.5 — миссии без подсветки/буззера, живой радар, hand вверх/вниз без встряски, YOLO v5 с автозагрузкой, скорость геймпада в панели

Правка по списку пожеланий владельца робота (проверка v1.6.4 на железе).

* **Missions: подсветка и буззер убраны из миссий** — миссия только двигает
  шасси. Из встроенной turn_show удалены шаги led (rainbow/off) и beep,
  шаги led/beep убраны из валидатора и исполнителя. Старые сохранённые
  сценарии, в которых были led/beep шаги, продолжают запускаться:
  валидатор молча их пропускает (без ошибки).
* **Radar: точки больше не пропадают** — «нет эха» теперь значит «свободно
  до 2 м»: каждый угол скана даёт точку — препятствие красной точкой на
  реальной дистанции, свободное направление — тускло-зелёной у внешней
  дуги (200 см). Раньше углы без эха отдавали None/0, канва их пропускала,
  и радар выглядел пустым («объектов нет»), хотя скан шёл. Если HC-SR04 не
  инициализирован, скан не запускается молча: в логе предупреждение, а на
  канве радара — сообщение «HC-SR04 offline» (в /api/status новый флаг
  `ultra_ok`).
* **trackHand: отключение по «встряске» убрано + слежение вверх/вниз** —
  режим идёт, пока владелец сам его не остановит (раньше 5 смен знака
  панорамы за 1.5 с выключали режим: «встряхнули руку = хватит»). Наклон
  камеры (tilt) теперь реально следует за рукой вверх/вниз: дробные шаги
  копятся в аккумуляторе — раньше int() съедал малые отклонения (шаг был 0
  при отклонении руки меньше ~30 % кадра), и tilt почти не двигался —
  выглядело как «следит только вправо/влево». Направление серво на случай
  зеркального крепления меняется флагами CAM_PAN_TRACK_DIR /
  CAM_TILT_TRACK_DIR (config.py), без правки кода.
* **YOLO: готовая модель скачивается сама в setup.py** — этап [8/8]
  загружает официальный yolov5n.onnx (YOLOv5 nano, 1.9M параметров, вход
  640×640, 3.8 МБ) из релиза ultralytics/yolov5 v7.0, целостность — по
  SHA-256 (config.YOLO_MODEL_SHA256), classes.txt (COCO-80) создаётся
  рядом; пропуск — PICARPRO_SKIP_YOLO=1. Замер cv2.dnn (CPU): чтение +
  инференс — пик ~150 МБ RSS, режим работает при 500 МБ свободной ОЗУ
  вместе с MJPEG-стримом. На RPi 3B+ детект ~1.5–3 с/кадр (поток видео не
  тормозит — инференс в отдельном потоке CVThread). Быстрый вход 320 или
  своя модель — tools/fetch_yolo.py; docs/YOLO_GUIDE.md переписан. Заодно
  проверено: сторонние ONNX, экспортированные свежими opset (например
  yakhyo/yolov5-onnx-inference), cv2.dnn НЕ читает — держитесь
  официального v7.0 или экспорта opset 12.
* **Геймпад: фактическая скорость видна в веб-панели** — в get_status
  контроллера добавлены drive_speed (текущая скорость хода 0–100) и turbo,
  блок ds4.* отдаётся в /api/status. Статус-бар панели: удержание L2/R2 —
  «100 %» оранжевым (турбо-потолок), движение без турбо — текущая скорость
  геймпада, без геймпада — ползунок веб-панели как раньше. При
  отключении геймпада drive_speed сбрасывается в 0.
* **Тесты**: миссии без led/beep (валидатор пропускает старые шаги),
  радар — ни одной точки без дистанции, trackHand — «встряска» не
  выключает режим и tilt реагирует на руку вверх/вниз, drive_speed/turbo
  в статусе геймпада. Полный набор: 518 passed, 1 skipped.

## MOD v1.6.4 — геймпад без лишних режимов, Tetris в буззере, Side lights в фарах, радар камерой, адаптивное энергосбережение

Правка по списку пожеланий владельца робота (проверка v1.6.3 на железе).

* **Геймпад: убраны режимы △ CV line, □ Hand track, Options Police+turbo,
  Share Police, PS Home all servos** — кнопки больше ничего не запускают
  (автономные режимы остались в веб-панели Autonomous). L2/R2 теперь
  «скорость 100 %», но БЕЗ принудительного движения вперёд: раньше турбо
  само везло машину вперёд с нейтральным стиком; теперь факт движения и
  направление задаёт только левый стик, а при L2/R2 потолок скорости = 100 %.
  Правый стик камеры двигает серво ШАГОМ РОВНО 5° (DS4_CAM_STEP_DEG) и не
  чаще, чем раз в DS4_CAM_STEP_INTERVAL_S (0.15 с) — раньше шаг рос с
  отклонением стика до 6° за событие при десятках событий в секунду и камера
  «улетала».
* **Buzzer: мелодия Birthday удалена, добавлен Tetris 8-bit** — Korobeiniki,
  полный проход темы A+B, монофония square-wave 50 % duty (как в Game Boy),
  ровно ~10 секунд (32 четверти × 0.3125 с). Кнопка «Tetris 8-bit» в панели
  Buzzer и команда `buzzer {melody: tetris}`.
* **Окно фар: добавлены Side lights** — кнопка габаритов (каналы 0/1
  switch-модуля, те же, что у L1 на геймпаде) в разделе Headlights & Signals,
  команда `side_lights {action: on|off|toggle}`, состояние в `/api/status`
  (side_lights) и синхронизация кнопки из телеметрии.
* **Radar сканирует камерой, а не колёсами** — ULTRASONIC_SCAN_SERVO =
  SERVO_CAM_PAN: раньше радар качал РУЛЕВОЕ серво, и машина «виляла
  колёсами» на месте; теперь качается панорама камеры, шасси неподвижно.
* **Grip tilt high убран** — позиции клешни low (100°) / mid (135°),
  CRANE_GRIP_HIGH (180°) удалён из config, команд (grip_high отклоняется),
  UI (кнопка High) и геймпад-цикла; servo_home ставит mid.
* **Энергосбережение камеры адаптивное** — по загрузке системы
  (max из CPU и RAM, SystemInfo): интервал фонового захвата плавно растёт
  до 3 × base при загрузке выше 80 % (ядра отдаются стриму/CV), а полный сон
  CSI-камеры не включается при загрузке выше 85 % — раньше пробуждение
  камеры под нагрузкой занимало секунды, и «при малом простое процессора и
  памяти всё лагало». Новые константы: CAMERA_IDLE_BACKOFF_CPU_PCT,
  CAMERA_IDLE_BACKOFF_MAX, CAMERA_SLEEP_SKIP_CPU_PCT.
* Тесты обновлены: turbo без стика не едет, камера шаг 5° + rate-limit,
  удалённые режимы — no-op, Tetris ~10 с, grip low/mid, side_lights.

## MOD v1.6.3 — переписан Bluetooth-модуль: сопряжение больше не стирается, надёжный вывод bluetoothctl, диагностика

Правка по итогам проверки v1.6.2 на железе: скан/подключение геймпада по
Bluetooth работали ненадёжно, автоподключение при загрузке портило сопряжение.

* **Автоподключение стирало сопряжение.** При загрузке робота геймпад обычно
  ещё выключен: «прямое подключение» не удавалось, и старый код делал
  `remove` + полное спаривание, которое без режима сопряжения тоже падало —
  после каждой загрузки геймпад приходилось спаривать заново. Теперь
  `remove` выполняется только при реально устаревших ключах
  (AuthenticationFailed и т.п.), а автоподключение (`auto_reconnect`,
  boot.py) вообще не спаривает — только `connect` уже сопряжённого, с
  повторами, пока служба Bluetooth поднимается.
* **Потерянный и «грязный» вывод.** stdout bluetoothctl читался через
  `select` поверх текстовой обёртки (данные застревали в её буфере), ANSI-
  цвета ломали разбор приглашения и событий. Теперь отдельный поток-читатель
  разбирает сырые байты, чистит ANSI и приглашение, собирает устройства из
  событий `[NEW]/[CHG]/[DEL] Device` (имя, RSSI, paired/trusted/connected).
* **Скан показывал устаревший кэш BlueZ** без RSSI и статусов. Теперь в
  списке только устройства из текущего скана плюс сопряжённые/подключённые —
  состояние выключенного, но сопряжённого геймпада берётся из `info`.
* **Параллельные запросы портили диалог с bluetoothctl** — операции
  сериализованы (`BluetoothBusy` второму запросу), после `remove` пара идёт
  только после повторного обнаружения сканом.
* **Диагностика и понятные сообщения**: `/api/bt/diagnose` (служба bluetooth,
  rfkill, адаптер, hid_sony), классификация ошибок подключения («геймпад
  выключен», «сопряжение устарело», «введите режим сопряжения Share + PS»)
  вместо безликого «Pairing failed». UI скана показывает RSSI и статусы,
  имена устройств выводятся через textContent (имя из эфира — не XSS-вектор).
* Безопасность сохранена: строгая валидация MAC (newline-injection), атомарная
  запись конфига с лимитом размера.
* Тесты: `tests/test_bluetooth_v163.py` на имитаторе bluetoothctl
  (`tests/fakes/fake_bluetoothctl.py` — цветной вывод, приглашение без \n,
  сценарии ошибок), регресс-тест «выключенный геймпад не теряет сопряжение».

## MOD v1.6.2 — дуговые развороты, сохранение маршрута, WS2812 на GPIO12, ИК-полярность, радар с точками, клешня на канале 5

Правка по итогам проверки v1.6.1 на железе: миссии не поворачивали,
записанный маршрут не сохранялся, WS2812 не работала, IR Line Sensors
показывали LINE всегда, режимы radar/drive/distance бесполезны,
crane tilt стоит на серво 5.

* **Развороты: дуга вместо «танкового» spin (корень «не может повернуться»)**.
  Шасси PiCarPro — Аккерман (рулевое серво, управляемые передние колёса):
  разворот на месте бортами в противоход физически не вращает машину —
  передние колёса скребут пол. Поэтому `turn` в миссиях и объезд препятствий
  не могли повернуть робота. Новый общий `drive.arc_turn()`: руль до упора
  (`STEER_MAP` 30/150) + ход вперёд `AUTO_TURN_ARC_SPEED`; угол закрывается
  по гироскопу MPU6050 (упреждение lead), без него — по времени
  (`AUTO_ARC_RATE_DPS = 80 °/с`, подстраивается в config.py). После
  разворота руль возвращается прямо. Обновлены миссии (`_turn`),
  автономный объезд (`_turn`) и встроенная миссия `spin_show` ->
  `turn_show` (двойной разворот дугой). Разворот на 180° требует свободного
  места впереди — как у настоящей машины.
* **Записанный маршрут не сохранялся: «bad dir: steer_left»**. Валидатор
  миссий отклонял шаги `steer_left/steer_right` (руление A/D без движения),
  из-за чего маршрут, записанный с поворотами руля, не сохранялся. Теперь
  эти шаги легальны (`drive()` умеет их исполнять), а из «вернуться домой»
  они выкидываются — руление на месте не смещает робота. Проверено
  тестом командного слоя: `record_stop` с `save_as` сохраняет JSON.
* **WS2812: найден корень многолетней «неработающей ленты»**. Лента
  подключена к **GPIO12 (PWM0, физ. пин 32)** — так в оригинальной прошивке
  Adeept (Server/RobotLight.py: `LED_PIN=12, LED_DMA=10, LED_CHANNEL=0`
  через rpi_ws281x) и в docs/components/ws2812.json. Все версии мода
  v1.0..v1.6.1 выводили сигнал в SPI MOSI (GPIO10, пин 19), куда лента не
  подключена. Новый бэкенд `LED_BACKEND='auto'`: rpi_ws281x на GPIO12
  (штатный путь setup.py уже ставит пакет), фолбэк — SPI с исправленными
  таймингами (запрос 2.4 МГц: T1H 512–1024 нс, T0H 256–512 нс, период
  768–1536 нс — в окне декодирования; в v1.6.1 при 7.8125 МГц T1H=256 нс —
  все биты декодировались как «0»). rpi_ws281x требует root — сервис уже
  работает от root; аналоговый звук 3.5 мм с лентой несовместим (общий
  PWM0), зуммер GPIO24 не конфликтует.
* **IR Line Sensors показывали LINE на голом полу**. `get_ir_values()`
  отдавал сырой GPIO (1 над белым), а UI трактовал 1 как LINE — ровно
  наоборот относительно логики следования (`==0` = линия). Теперь оба
  читателя возвращают семантику «линия обнаружена»; полярность модуля —
  флаг `LINE_ACTIVE_LOW` в config.py (по умолчанию True: над тёмной
  линией датчик отдаёт LOW; для модуля с обратной полярностью — False в
  config_local.py).
* **Radar как в оригинале: живой сектор с точками**. Скан больше не
  останавливается после одного прохода: качает датчик туда-сюда
  (`ULTRASONIC_SCAN_SERVO`), точки обновляются по углам и уходят в статус
  (`radar_data`). В UI под кнопкой Radar — канва с сектором ±60°,
  дистанционными дугами 50/100/150/200 см и красными точками
  препятствий. Бесполезные кнопки Drive (automatic) и Distance
  (keepDistance) из панели убраны (режимы остались в API и миссиях;
  объезд препятствий при этом починен дуговым разворотом).
* **Клешня: наклон на канале 5** (по прямому указанию владельца с железа —
  «crane tilt стоит на серво 5»): `SERVO_CRANE_GRIP=5` (наклон, полный
  диапазон 0..180), `SERVO_CRANE_ARM=6` (захват, 100..180), канал 4
  (локоть) — резерв. UI: ползунок 5 «Crane Tilt», 6 «Crane Grab», кнопки
  Low/Mid/High и Grab/Release двигают те же каналы.
* Тесты: `tests/test_v162.py` (13 новых: дуговый разворот — руль/моторы/
  стоп/центр, гироскоп-контур, сохранение маршрута с рулением командным
  слоем, бэкенд pwm GPIO12 + SPI-фолбэк 2.4 МГц, полярность ИК,
  turn_show); обновлены радар-тест (непрерывный скан) и
  `test_ir_values_api` (семантика «линия»).

## MOD v1.6.1 — управление без инверсий: WASD, стрелки/джойстики/геймпад, клешня, WS2812

Правка по итогам проверки на железе после v1.6.0: инверсия WASD, сломанные
arm/grip tilt, неработающая WS2812-лента.

* **Инверсия WASD убрана (пины моторов возвращены к заводским)**: в v1.6.0
  пары IN1/IN2 обоих бортов ошибочно поменяли местами (A_IN1=21, B_IN1=18),
  из-за чего на роботе «w» ехал назад, а «s» — вперёд. Вернули заводскую
  разводку Adeept v1 (урок 6 «How to Control DC Motor»:
  `Motor_A_Pin1 = 26`, forward = Pin1 HIGH; то же соответствие — в исходном
  коде jsck37: `Motor(forward=MOTOR_A_IN1=26)`). Теперь:
  `MOTOR_A_IN1=26, MOTOR_A_IN2=21, MOTOR_B_IN1=27, MOTOR_B_IN2=18`.
  Спецификация управления: **w — вперёд, s — назад, a — влево, d — вправо**.
  Для сборок с перепутанными проводами остаются флаги
  `MOTOR_INVERT_RIGHT/LEFT` в config.py (перевернуть борт без пайки).
* **Инверсия камеры убрана — везде по одной спецификации**
  («стрелка = камера движется в ту же сторону»):
  - клавиатура (стрелки и I/J/K/L): **вверх = tilt +5°** (камера
    поднимается; в v1.6.0 «вверх» опускал камеру), **вниз = tilt −5°**,
    **вправо = pan −5°**, **влево = pan +5°** (на этом серво «вправо» =
    меньший угол — как на руле: 30 = право, 150 = лево). Таблица дельт
    вынесена в `panel-core.js` (`PanelCore.camKeyDelta`) и покрыта
    node-тестами;
  - джойстик камеры в UI: драг в ту же сторону, что стрелки — раньше
    драг вправо увеличивал pan (камера уходила ВЛЕВО), а драг вверх
    уменьшал tilt (камера опускалась). Теперь `PanelCore.stickToCam`:
    драг вверх = камера вверх, драг вправо = панорама вправо;
  - геймпад DS4 (правый стик): стик вправо = камера вправо (pan меньше) —
    раньше было наоборот. Стик вверх = камера вверх (не менялось).
* **Клешня: каналы возвращены к фактической проводке робота** — по
  исходному config.py jsck37: канал 4 = плечо/наклон клешни
  (`SERVO_CRANE_GRIP` — кнопки Grip tilt и ползунок «Crane Tilt»),
  канал 6 = захват (`SERVO_CRANE_ARM` — кнопка Grab/Release и ползунок
  «Crane Grab»), канал 5 (кисть) на этой сборке не подключён. В v1.6.0
  каналы ошибочно взяли из общей доки Adeept (4/5) — после этого
  перестали работать и кнопки, и ползунки: захват уехал на канал 5,
  наклон остался в урезанном диапазоне 100..180 (рабочий ход наклона
  лежит и ниже 100°). Теперь `SERVO_LIMITS[4] = 0..180` (полный диапазон,
  как в v1.5.x), `SERVO_LIMITS[6] = 100..180`; подписи ползунков Servo:
  4 = «Crane Tilt», 5 = «Servo 5», 6 = «Crane Grab»; подсказка в карточке
  Crane обновлена. `COLOR_SCAN_GRIP_SERVO = 6` снова совпадает с захватом.
* **WS2812 (led strip) починена**: кодирование сигнала переведено на
  классическую схему «3 SPI-бита на бит WS2812» при запросе 8 МГц
  (`_BIT1 = 0b110`, `_BIT0 = 0b100`). На bcm2835 делитель SPI округляется
  вниз до степени двойки: запрос 6.4 МГц в v1.0..v1.6.0 давал фактические
  7.8125 МГц, из-за чего T0H был 256 нс и чип декодировал «ноль» как
  «единицу» — лента светила белым мусором вместо цветов (зафиксировано
  ещё в проверке железа v1.4.0, «лечилась» только диагностикой). Теперь
  при тех же фактических 7.8125 МГц: T1H = 256 нс, T0H = 128 нс,
  период 384 нс — стандартная проверенная схема (как в rpi_ws281x
  SPI-fallback). Задержка защёлки 90 нулевых байт = 92 мкс (≥ 50 мкс).
* Тесты: обновлены пиновые тесты моторов (26/27 = forward), LED-биты

## MOD v1.3.4 — точка доступа становится основным режимом Wi-Fi

По репорту пользователя: после v1.3.3 скрипт отрабатывает, но точки доступа
нет, к машинке подключиться нельзя. Объяснение: логика «домашняя сеть
прежде точки доступа» — если NetworkManager авто-подключился к сохранённой
Wi-Fi-сети, скрипт честно завершался с exit 0 и AP не поднималась. Для
машинки это неверная приоритезация: телефон должен подключаться к роботу
напрямую, как в оригинальном Adeept.

  перед этим активное клиентское подключение отключается (иначе NM не даст
  поднять AP на том же радио), что решает и сценарий «Pi прицепился к
  домашнему Wi-Fi при загрузке»;
* режимы auto (домашняя сеть прежде AP — прежнее поведение) и client
  (никогда не поднимать AP) доступны как выбор при установке и в
  /etc/picarpro/hotspot.conf (HOTSPOT_MODE="..."), меняются одной строкой
  без переустановки;
* **канал AP зафиксирован на 6**: auto-выбор канала иногда попадает на 12/13,
  которые большинство телефонов не сканируют — «AP поднята, но не видна»;
* **устанавливается dnsmasq-base**: NM в режиме shared вызывает dnsmasq для
  DHCP/DNS клиентов точки доступа — без него телефон подключается к AP, но
  не получает IP (и активация может падать);
* повторный запуск сервиса при уже работающей AP больше не перезапускает её
  (проверка активного подключения — без «отваливания» точки доступа на
  service restart);
* в лог добавлены URL веб-интерфейса (http://10.42.0.1:5000) и подсказка
  про dnsmasq при ошибке активации.

Тесты: mocked-nmcli прогоны обеих веток (hotspot: сразу AP при наличии
сохранённой домашней сети; auto: неудача клиента -> fallback на AP);

## MOD v1.3.3 — сервис Wi-Fi ждёт wlan0 (фикс «no suitable device found»)

По репорту пользователя: picarpro-wifi.service при загрузке падает с
«connection activation failed: no suitable device found for this connection
(device eth0 not available because profile is not compatible with device)».

Причина — гонка на старте: скрипт ждал только NetworkManager
(`nmcli general status`), но не сам Wi-Fi-интерфейс. brcmfmac на Raspberry Pi
подгружает прошивку уже ПОСЛЕ того, как NM-юнит считается запущенным, поэтому
в момент `nmcli con up` устройства ещё не существовало: NM не находил ни
одного Wi-Fi-устройства, единственным кандидатом оставался eth0 — к нему
wifi-профиль несовместим по типу, что и написано в ошибке.

* сгенерированный /usr/local/bin/wifi_hotspot_manager.sh теперь дожидается
  появления Wi-Fi-интерфейса до 60 с; интерфейс определяется динамически
  (nmcli -t -f DEVICE,TYPE dev status), а не захардкожен как wlan0 —
  переименование интерфейса больше не ломает hotspot;
* перед ожиданием снимается rfkill-блокировка и включается радио
  (`rfkill unblock wifi`, `nmcli radio wifi on`): после сбоев питания NM
  может держать Wi-Fi выключенным;
* статус «уже подключено к известной сети» проверяется по состоянию
  устройства (`802-11-wireless:connected`), а не по скану эфира
  (`dev wifi list`) — скан на только что появившемся интерфейсе бывает
  пустым и давал ложное «не подключено»;
* при отсутствии интерфейса за 60 с или неудачной активации — понятная
  строка в лог с командами диагностики и exit 1 (вместо молчаливого
  «Hotspot started successfully» при упавшем hotspot);
* picarpro-wifi.service: Restart=on-failure, RestartSec=15,
  StartLimitIntervalSec=0 — разовый сбой больше не оставляет машинку без
  hotspot'а до следующей перезагрузки, сервис перезапускается сам.

## MOD v1.3.2 — ленивый старт серво (устранение ребута при загрузке)

Мануал Adeept (Robot HAT, «Precautions») подтверждает: пик тока робота
~3.75 А при 7.4 В (нужна батарея от 4 А), и ребут происходит в момент,
когда программа при старте выводит все серво в нейтраль — просадка питания
роняет Raspberry Pi. Наша прошивка делала ровно это: `ServoController`
в `_init_pca9685()` дёргал все 7 каналов к init-углам с интервалом 30 мс
сразу после старта сервиса.

  каналы создаются, но PWM не пишется — выходы чипа остаются выключенными,
  серво не получают импульсов и не потребляют ток. Пусковой бросок тока в
  момент старта сервиса устранён полностью; первое движение серво
  происходит по первой команде, по одному за раз (ток одного серво ~1 А —
  в пределах любого исправного питания);
* **дедупликация анти-джиттера учитывает ленивый старт**: первый после
  загрузки угол пишется всегда (физическое положение серво неизвестно),
  повторные команды того же угла — по-прежнему не пишутся;
* `get_angle()`/`get_angles()`: для ещё не двигавшихся каналов возвращается
  целевой init-угол — веб-интерфейс и статус работают как раньше;
* **config.py: SERVO_MOVE_ON_BOOT** (по умолчанию False). True — старое
  поведение (вывод всех серво в нейтраль при загрузке), нужно ТОЛЬКО при
  сборке для установки качалок серво (урок 9 мануала), и то при питании
  от батареи 4А+ или USB с выключателем Vin в OFF;
* `smooth_move()` по не двигавшемуся серво делает один прямой ход вместо
  интерполяции из вымышленной стартовой точки.

По логу реальной установки: системная часть прошла идеально (apt

импорта, а не на реальное отсутствие пакета.

* **таймауты убраны совсем**: раньше установщик сам убивал команду по

  недостающих пакетов и предупреждение «может занять 10-30 минут»;

  журнал сбрасывался одним куском в конце — при выключении питания или

  — причина видна сразу, без чтения лога;
* при ошибке любой команды в консоль печатаются последние строки её
  вывода (не только отсылка к логу); декодирование вывода устойчиво к
  бинарному мусору (`errors='replace'` — раньше такой вывод ронял
  установщик с UnicodeDecodeError).

## MOD v1.2.0 — оптимизация CPU/RAM (под Pi 3B+ с 1 ГБ ОЗУ)

Профилирование показало, что даже в простое прошивка жгла существенную
долю CPU и ОЗУ. Главные источники: JPEG-кодирование каждого кадра при
отсутствии зрителей, активное ожидание эха HC-SR04, телеметрия 1 Гц,
50 пробуждений/с в IMU-стриме и рабочие потоки BLAS по числу ядер.

* **камера работает по требованию (главное)**: JPEG-кодирование и
  CV-обработка выполняются только при наличии потребителей — открытый
  `/video_feed`, активный CV-режим, либо зарегистрированный raw-
  потребитель (ArUco-навигация, color_scan). Без потребителей поток
  захвата спит 0.5 с (`CAMERA_IDLE_INTERVAL_S`) — экономия до 60-80%
  одного ядра в простое; открытие вкладки с видео мгновенно возвращает
  полный ритм (15 fps);
* **снижена цена каждого кадра**: `CAMERA_FPS` 30 → 15 и
  `CAMERA_JPEG_QUALITY` 75 → 60 (для web-MJPEG и CV-режимов этого
  достаточно, трафик на клиента упал ~в 2.5 раза); убрана лишняя копия
  кадра ~0.9 МБ в `submit_frame` (capture_array и так отдаёт свежий
  буфер, CV-режимы вход не мутируют);
* **HC-SR04 без busy-wait**: ожидание эха переведено на событийное
  `GPIO.wait_for_edge(timeout)` — раньше активное кручение GPIO.input
  жгло до 50% ядра при отсутствии препятствия (полный таймаут ожидания
  на каждом цикле опроса); для сред без wait_for_edge (фейки тестов)
  оставлен прежний путь;
* **телеметрия 2 Гц**: WS-броадкаст статуса и SSE-поток идут раз в
  `TELEMETRY_INTERVAL_S = 2.0` вместо 1 Гц — `get_status()` читает
  I2C/GPIO и собирает большой словарь; опрос vcgencmd (подпроцесс)
  разрежен до 3 с (`VOLTAGE_CHECK_INTERVAL_S`);
* **IMU-стрим**: без подписчика спим 0.25 с вместо 50 пробуждений/с;
  при активном подписчике точный ритм 20 Гц сохранён;
* **лимиты потоков BLAS/OMP**: systemd-юнит и boot.py задают
  `OMP/OPENBLAS/MKL/NUMEXPR_NUM_THREADS=2` — по умолчанию OpenBLAS
  создаёт рабочий поток на ядро с крупными стеками (лишняя ОЗУ и
  синхронизация); на YOLO/numpy при 4 ядрах это не влияет;
* **YOLO**: плашка «YOLO MODEL NOT FOUND» рисуется один раз, а не
  на каждом кадре (3 cvtColor + putText экономим);
* **память**: кольцевой буфер логов 2000 → 800 строк (~150 КБ);
* **WebSocket**: `compression=None` (сжатие мелких JSON дороже, чем
  выгодно), ping 30 с, очередь 4 — меньше сисколов на сообщение.

Совместимость: все команды, режимы и UI без изменений; при открытом
видео частота потока 15 fps — субъективно плавность почти та же,
нагрузка вдвое ниже. Если нужно вернуть 30 fps — `CAMERA_FPS = 30`
в config.py.

## MOD v1.1.3 — само-лечащийся установщик (по логу пользователя)

В логе реальной установки на Trixie были две ошибки: (1) apt отвергал
любую установку из-за сломанных зависимостей частичного обновления
(chromium-l10n 155 при chromium 147; libcamera 0.7.2 при 0.7.1) —
поэтому не встали bluetooth/pi-bluetooth; (2) ВСЕ pip-пакеты «не
установлено» с пустым выводом в логе — процессы pip убивались

Взятые из старого stage-установщика репозитория идеи (swap до pip,
apt upgrade, python3-opencv из apt) встроены в тихий установщик:

* **авто-починка apt ДО установки**: проба `apt-get -s install` ->
  `dpkg --configure -a` -> `apt --fix-broken install` -> (если не
  помогло) `apt full-upgrade -y -o Dpkg::Options::=--force-confold`;
* **swap 2 ГБ до pip**: если ОЗУ+swap < 2 ГБ, установщик сам вызывает
  `tools/setup_swap.sh` (dphys-swapfile + swappiness) — раньше это был
  ручной шаг, о котором легко забыть; именно без него pip гиб от OOM;
* **apt-first для тяжёлых пакетов**: numpy/opencv/pillow/flask/
  websockets/loguru/smbus2/evdev/spidev ставятся из apt (пред собранные,
  без компиляции на 1 ГБ); отсутствующие в репозитории (python3-luma-oled,
  python3-rpi.gpio вне RPi-репо) отсеиваются `apt-cache show` и идут в pip;
* **pip с фолбэком**: батч `--prefer-binary` + поштучная доборка — один
  кривой пакет больше не топит остальные;
* **статус по импорту модуля**, а не по pip list (apt-пакеты вроде
  python3-opencv в pip list не видны — раньше это давало ложные
  «НЕ установлено»); для opencv дополнительно проверяется `>=4.7` —
  на bookworm/bullseye apt-версия старее, тогда берётся из pip;
* **диагностируемость**: PYTHONUNBUFFERED=1 у всех дочерних процессов
  (вывод не теряется даже при гибели процесса), в лог пишется
  `--- exit: N ---` и маркеры таймаута/Ctrl+C; при неудаче в консоль
  печатаются последние строки лога;
* `dphys-swapfile` добавлен в список apt-пакетов (нужен для swap);
  DEBIAN_FRONTEND=noninteractive — apt не задаёт вопросов.

## MOD v1.1.2 — тихий установщик: «установлено / НЕ установлено»

По запросу: установщик больше не заливает консоль выводом apt/pip
(на сломанном apt это были сотни строк повторов).

* весь вывод всех команд (apt update/install, pip, raspi-config,
  systemctl) захватывается и пишется в `/tmp/picarpro-setup.log`;
* в консоли по каждому пакету печатается ровно одна строка статуса:
  `имя    установлено` / `имя    НЕ установлено` — отдельно для
  apt-пакетов и для pip-зависимостей из requirements.txt;
* статус определяется не по коду возврата apt, а по факту:
  `dpkg-query` для apt-пакетов, `pip3 list` для Python-пакетов;
* если apt-пакеты не установились, установщик печатает готовую команду
  лечения системы частичного обновления:
  `sudo apt update && sudo apt full-upgrade -y && sudo apt --fix-broken install -y`;

  (раньше — только при успешной apt-установке): если apt сломан,
  pip-установка остальных пакетов больше не срывается из-за неё;
* при неудаче pip-зависимостей установщик завершается с ошибкой ДО
  установки сервисов — чтобы не включать автозапуск прошивки, которая

* сервер валидирует лимиты как и раньше (`_clamp` в ServoController) —
  случайное изменение невозможно ни в UI, ни по прямым командам;
* синхронизация углов из статуса (servo_angles) с защитой от перезаписи
  поля в фокусе.

### Прочее
* boot.py: запуск NavTCP + IMU-стрима, корректная остановка при выходе;
* state.py: новые компоненты (aruco_nav, pusher, color_scan, nav_server,
  imu_stream) + расширенный статус (yolo, nav_tcp, aruco_nav, push,
  color_scan);
* config.py: секции YOLO_*, ARUCO_*, NAV_TCP_PORT=5001, IMU_UDP_PORT=5005,
  OBSTACLE_PUSH_*, COLOR_SCAN_*;
* commands.py: команды `yolo_status`, `aruco_nav`, `push`, `color_scan`,
  cv-режим `yoloDetect`;
* docs: YOLO_GUIDE.md, MEMORY_TUNING.md, ARUCO_NAV.md; README дополнен.

## 2. Безопасность

1. **MAC-инъекция в bluetoothctl** (`routes/bluetooth.py`): MAC из запроса
   уходил в stdin bluetoothctl без валидации — перевод строки в MAC позволял
   внедрить произвольные команды (`remove *`, `quit`). Добавлена строгая
   валидация `^([0-9A-Fa-f]{2}:){5}[0-9A-Fa-f]{2}$` (`validate_mac`), все
   точки входа проверяют формат.
2. **CORS `*`** (`web/app.py`): wildcard CORS удалён. Белый список задаётся
   `PICARPRO_CORS` (по умолчанию CORS полностью выключен — UI одностраничный
   и same-origin).
3. **Опциональная токен-авторизация** (`web/auth.py`): при заданном
   `PICARPRO_TOKEN` все `/api/*` и `/cmd/*` и WebSocket требуют токен
   (заголовок `X-Auth-Token`, `?token=`, либо первое WS-сообщение
   `{"cmd":"auth"}`). Сравнение через `hmac.compare_digest` (timing-safe).
4. **SECRET_KEY** больше не константа `'picarpro'`: из окружения либо
   автогенерация `secrets.token_hex(32)` с сохранением в
   `instance/secret_key` (chmod 600).
5. **Заголовки безопасности**: `X-Content-Type-Options`, `X-Frame-Options:
   DENY`, `Referrer-Policy`, CSP без inline-скриптов.
6. **`MAX_CONTENT_LENGTH`** = 1 MiB на запрос.
7. **Path traversal** в `/docs/components/<fn>` — блокировка `..`.
8. **Утечка стека** в WS-ответах об ошибках обрезана до 200 символов.
9. Из унаследованных уязвимостей оригиналов НЕ перенесены: логин
   `admin:123456` по открытому WS, пароль точки доступа `12345678` как
   единственная защита, APPServer без аутентификации, `os.system` с
   конкатенацией, захардкоженный ключ DeepSeek в Examples v2
   (`sk-cb36...` — ключ отозван не был, упомянут в README).

## 3. Ошибки памяти / ресурсов

1. **Голосовой запуск сломан полностью** (`functions/voice_command.py:57-63`
   в jsck37): дескриптор `open(...)` открывался в `with`-блоке и ЗАКРЫВАЛСЯ
   до `Popen(stdout=f)` — Popen получал закрытый файл, голосовое управление
   никогда не стартовало. Фикс: дескриптор хранится в `self._sherpa_log`,
   закрывается в `_stop_sherpa`.
2. **Subprocess-шторм IP** (`network.py`): `get_ip()` вызывал до 4
   subprocess `ip addr show` на каждый тик статуса (раз в секунду на
   каждого клиента). Добавлен кэш на 30 с (`reset_ip_cache` для тестов).
3. **Sleep в обработчике запроса** (`utils/system_info.py`):
   `get_cpu_usage()` спал 0.3 с внутри каждого запроса статуса. CPU/RAM
   теперь собирает фоновый поток-сэмплер с кэшем (2 с), ответы отдаются
   мгновенно.
4. **Утечка потоков сглаживания крана** (`hardware/ds4.py`): каждое нажатие
   кнопки порождало новый поток `_smooth_crane`. Частые нажатия = dozens
   threads. Теперь цель хранится в `_smooth_targets` — активный поток
   подхватывает новую цель, новые потоки не создаются.
5. **Гонка set()+clear()** (`camera/camera_opencv.py`):
   `_frame_ready.set(); _frame_ready.clear()` подряд — ожидающий поток мог
   никогда не проснуться (кадры «зависали»). Событие теперь остаётся
   установленным до следующего кадра.
6. **Пересоздание I2C/PCA9685** из оригиналов (RPIservo.py:63-69 v1/v2 —
   новый объект на каждое движение сервы) в jsck37-архитектуре уже было
   исправлено (один контроллер с локом) — поведение сохранено и покрыто
   тестами.
7. **video_feed без камеры** возвращал вечный пустой MJPEG-поток — теперь
   честный `503 Camera not available`.
8. **ADS7830-монитор** проверяет наличие АЦП на шине до создания ридера —
   без АЦП не держит открытый SMBus.

## 4. Ошибки логики (найдено и исправлено при слиянии)

1. **`trackLine` выпадал из списка режимов** — при переносе списков
   `MODES_WITH_ULTRA + MODES_WITH_CAMERA` строка `trackLine` отсутствовала в
   `ALL_MODES`, и режим IR-линии отбрасывался валидатором. Исправлено,
   покрыто тестом.
2. **`safe_int` везде** (`commands.py`): `int(params)` без try ронял
   обработчик WS-команд на мусорном вводе (`servo id='abc'` → ValueError).
   Все числовые параметры парсятся безопасно с ограничением диапазона;
   `servo_set_limits` дополнительно разворачивает min>max.
3. **Неизвестные команды** теперь возвращают явную ошибку
   `Unknown command: ...` вместо молчаливого `ok: false`.
4. **Дублирование дифференциального привода** (`ds4.py` ↔ `motors.py`):
   `_motors_move_with_turn`/`_motors_single_turn` копировали логику
   `MotorController.move` с прямой записью в GPIO. Заменены общим методом
   `MotorController.move_differential(speed, dir, left, right)`.
5. **Направление findColor**: в v2 APPMode кадр конвертировался BGR2RGB
   вместо HSV перед inRange (camera_opencv v2:350-353) — режим не находил
   ничего. В порте HSV-конвертация корректна, m00 защищён от деления на 0.
6. **Кулдаун watchdog**: в оригинале тревога могла срабатывать каждый кадр;
   добавлены порог площади + кулдаун `WATCHDOG_COOLDOWN_S`.
7. **`watch_dog`/`findColor` callbacks отвязываются** в `stop()` — не
   остаётся висящих ссылок на автономный контроллер после смены режима.
8. **Команда `auto`** возвращает осмысленную ошибку при отказе
   (`Ultrasonic sensor not available` и т.п.) вместо `ok:false` без причин.

## 9. Установка

Без изменений по духу jsck37, но с двумя сервисами:

```bash
sudo python3 setup.py        # deps + picarpro.service + picarpro-hotspot.service
sudo systemctl start picarpro
```

Переменные окружения (опционально): `PICARPRO_TOKEN` (включить авторизацию),
`PICARPRO_SECRET_KEY`, `PICARPRO_CORS` (белый список через запятую).
