# CHANGELOG — PiCar-Pro Merged Edition v1.0.0

## MOD v1.3.5 — Wi-Fi переписан на hostapd + dnsmasq, SSH на уровне системы

По репорту пользователя: точка доступа так и не появляется (NM-вариант
падал трижды: «no suitable device found», затем «скрипт работает, но AP
нет»). Принято решение: NetworkManager-реализация полностью удаляется,
Wi-Fi-подсистема переписана на классический стек hostapd + dnsmasq — то,
чем пользовались оригинальные прошивки Adeept. hostapd говорит с драйвером
напрямую (nl80211) и не зависит от логики NM, wpa_supplicant'а и dnsmasq'а
самого NM.

* **fix_wifi_hostapd.sh** — единый идемпотентный скрипт перезаписи Wi-Fi;
  его вызывает установщик (stage 6), и его же можно запустить вручную на
  живой машине БЕЗ переустановки: `sudo bash fix_wifi_hostapd.sh`;
* **wlan0 навсегда изъят из NetworkManager**: постоянное правило
  /etc/NetworkManager/conf.d/picarpro-unmanage-wlan0.conf + подстраховка
  `nmcli device set wlan0 managed no` перед каждым стартом AP — NM больше
  не может перехватить интерфейс или авто-подключиться к чужой сети;
* **picarpro-hotspot.service**: hostapd во foreground под управлением
  systemd, Restart=always/5с; подготовка интерфейса — в ExecStartPre
  (ожидание wlan0 до 60 с, rfkill unblock, сброс линка, статический IP);
  сбой подготовки = перезапуск юнита — бесконечное самовосстановление;
* **picarpro-hotspot-dhcp.service**: собственный dnsmasq (dnsmasq-base, без
  системного сервиса, чтобы не занимать :53) раздаёт адреса клиентам AP
  (диапазон .50-.150 от IP машинки, router/DNS = IP машинки);
* runtime-конфиги генерируются при каждом старте из /etc/picarpro/hotspot.conf
  (HOTSPOT_SSID/HOTSPOT_PASS/HOTSPOT_CHANNEL/HOTSPOT_IP): правка файла +
  restart двух сервисов применяет настройки без переустановки;
* канал по умолчанию 6, WPA2-PSK (CCMP), ieee80211n, hw_mode=g;
* предыдущие артефакты (picarpro-wifi.service, wifi_hotspot_manager.sh,
  NM-профиль picarpro-hotspot, дистрибутивный hostapd.service) отключаются
  и удаляются автоматически;
* **SSH включён на уровне системы**: openssh-server ставится, ssh.service
  enable + start — к машинке можно подключаться `ssh <user>@10.42.0.1`
  сразу после подключения к точке доступа;
* HOTSPOT_MODE удалён (режимы больше не нужны — AP всегда); вместо него
  HOTSPOT_CHANNEL в config.py; +test_hotspot_channel_valid.

Мок-тесты: генерация всех артефактов, NM-правило, юниты (Restart/ExecStartPre),
runtime-конфиги (ssid/channel/wpa2/dhcp-range из префикса IP), enable ssh,
негатив (пароль <8 отклоняется).

## MOD v1.3.4 — точка доступа становится основным режимом Wi-Fi

По репорту пользователя: после v1.3.3 скрипт отрабатывает, но точки доступа
нет, к машинке подключиться нельзя. Объяснение: логика «домашняя сеть
прежде точки доступа» — если NetworkManager авто-подключился к сохранённой
Wi-Fi-сети, скрипт честно завершался с exit 0 и AP не поднималась. Для
машинки это неверная приоритезация: телефон должен подключаться к роботу
напрямую, как в оригинальном Adeept.

* **HOTSPOT_MODE (по умолчанию hotspot)**: точка доступа поднимается ВСЕГДА;
  перед этим активное клиентское подключение отключается (иначе NM не даст
  поднять AP на том же радио), что решает и сценарий «Pi прицепился к
  домашнему Wi-Fi при загрузке»;
* режимы auto (домашняя сеть прежде AP — прежнее поведение) и client
  (никогда не поднимать AP) доступны как выбор при установке и в
  /etc/picarpro/hotspot.conf (HOTSPOT_MODE="..."), меняются одной строкой
  без переустановки;
* **канал AP зафиксирован на 6**: auto-выбор канала иногда попадает на 12/13,
  которые большинство телефонов не сканируют — «AP поднята, но не видна»;
* **устанавливается dnsmasq-base**: NM в режиме shared вызывает dnsmasq для
  DHCP/DNS клиентов точки доступа — без него телефон подключается к AP, но
  не получает IP (и активация может падать);
* повторный запуск сервиса при уже работающей AP больше не перезапускает её
  (проверка активного подключения — без «отваливания» точки доступа на
  service restart);
* в лог добавлены URL веб-интерфейса (http://10.42.0.1:5000) и подсказка
  про dnsmasq при ошибке активации.

Тесты: mocked-nmcli прогоны обеих веток (hotspot: сразу AP при наличии
сохранённой домашней сети; auto: неудача клиента -> fallback на AP);
+test_hotspot_mode_valid.

## MOD v1.3.3 — сервис Wi-Fi ждёт wlan0 (фикс «no suitable device found»)

По репорту пользователя: picarpro-wifi.service при загрузке падает с
«connection activation failed: no suitable device found for this connection
(device eth0 not available because profile is not compatible with device)».
Профиль hotspot'а при этом создаётся успешно — падает именно активация.
Причина — гонка на старте: скрипт ждал только NetworkManager
(`nmcli general status`), но не сам Wi-Fi-интерфейс. brcmfmac на Raspberry Pi
подгружает прошивку уже ПОСЛЕ того, как NM-юнит считается запущенным, поэтому
в момент `nmcli con up` устройства ещё не существовало: NM не находил ни
одного Wi-Fi-устройства, единственным кандидатом оставался eth0 — к нему
wifi-профиль несовместим по типу, что и написано в ошибке.

* сгенерированный /usr/local/bin/wifi_hotspot_manager.sh теперь дожидается
  появления Wi-Fi-интерфейса до 60 с; интерфейс определяется динамически
  (nmcli -t -f DEVICE,TYPE dev status), а не захардкожен как wlan0 —
  переименование интерфейса больше не ломает hotspot;
* перед ожиданием снимается rfkill-блокировка и включается радио
  (`rfkill unblock wifi`, `nmcli radio wifi on`): после сбоев питания NM
  может держать Wi-Fi выключенным;
* статус «уже подключено к известной сети» проверяется по состоянию
  устройства (`802-11-wireless:connected`), а не по скану эфира
  (`dev wifi list`) — скан на только что появившемся интерфейсе бывает
  пустым и давал ложное «не подключено»;
* при отсутствии интерфейса за 60 с или неудачной активации — понятная
  строка в лог с командами диагностики и exit 1 (вместо молчаливого
  «Hotspot started successfully» при упавшем hotspot);
* picarpro-wifi.service: Restart=on-failure, RestartSec=15,
  StartLimitIntervalSec=0 — разовый сбой больше не оставляет машинку без
  hotspot'а до следующей перезагрузки, сервис перезапускается сам.

## MOD v1.3.2 — ленивый старт серво (устранение ребута при загрузке)

Мануал Adeept (Robot HAT, «Precautions») подтверждает: пик тока робота
~3.75 А при 7.4 В (нужна батарея от 4 А), и ребут происходит в момент,
когда программа при старте выводит все серво в нейтраль — просадка питания
роняет Raspberry Pi. Наша прошивка делала ровно это: `ServoController`
в `_init_pca9685()` дёргал все 7 каналов к init-углам с интервалом 30 мс
сразу после старта сервиса.

* **серво больше не двигаются при загрузке**: PCA9685 инициализируется,
  каналы создаются, но PWM не пишется — выходы чипа остаются выключенными,
  серво не получают импульсов и не потребляют ток. Пусковой бросок тока в
  момент старта сервиса устранён полностью; первое движение серво
  происходит по первой команде, по одному за раз (ток одного серво ~1 А —
  в пределах любого исправного питания);
* **дедупликация анти-джиттера учитывает ленивый старт**: первый после
  загрузки угол пишется всегда (физическое положение серво неизвестно),
  повторные команды того же угла — по-прежнему не пишутся;
* `get_angle()`/`get_angles()`: для ещё не двигавшихся каналов возвращается
  целевой init-угол — веб-интерфейс и статус работают как раньше;
* **config.py: SERVO_MOVE_ON_BOOT** (по умолчанию False). True — старое
  поведение (вывод всех серво в нейтраль при загрузке), нужно ТОЛЬКО при
  сборке для установки качалок серво (урок 9 мануала), и то при питании
  от батареи 4А+ или USB с выключателем Vin в OFF;
* `smooth_move()` по не двигавшемуся серво делает один прямой ход вместо
  интерполяции из вымышленной стартовой точки.

Тесты: +TestLazyBoot (нет записей PWM при старте; первая команда пишется
всегда; fallback на init-углы; smooth_move без интерполяции).

## MOD v1.3.1 — установщик откатен к версии 4870e2b (анти-ребут)

По репорту пользователя: машинка уходит в вечную перезагрузку. Установщик
заменён на проверенную версию из коммита 4870e2b (stage-схема 0–7), которая
радикально иначе работает со swap — главному подозреваемому в цикле ребутов:

* **все сбойные swap/zram-сервисы маскируются**: dphys-swapfile,
  systemd-zram-setup@zram0, zramswap (zram-tools), rpi-resize-swap-file,
  rpi-setup-resize, rpi-setup-loop@var-swap и unit dev-zram0.swap — их
  ошибки больше не могут влиять на загрузку (в оригинале так и было:
  «to prevent boot errors»);
* **статический swap 2 ГБ /var/swap через /etc/fstab** вместо dphys-swapfile:
  файл создаётся fallocate (fallback dd), chmod 600, mkswap, swapon;
  vm.swappiness=10 в /etc/sysctl.d/99-picarpro.conf;
* **вычистка настроек прежнего стека**: /etc/sysctl.d/99-picarpro-swap.conf
  (swappiness=80, vfs_cache_pressure=50, overcommit_memory=1) удаляется,
  чтобы не конфликтовать с новым (остаётся только swappiness=10);
* **анти-флап прошивки**: в picarpro.service добавлены StartLimitIntervalSec=60
  + StartLimitBurst=3 — краш-цикл сервиса не может бесконечно перезапускаться
  и выглядеть как «вечный ребут»;
* **адаптация под текущую структуру репозитория** (оригинал 4870e2b писался
  под Server/WebServer.py): точка входа boot.py, HOTSPOT_* из config.py в
  корне, добалены зависимости текущей прошивки — RPi.GPIO, spidev, smbus2
  (pip), python3-dev, python3-picamera2 + python3-libcamera на Debian 12+
  (apt); на Trixie do_camera не вызывается (удалён из raspi-config);
  итоговый отчёт печатает python3 boot.py;
* **защита от переполнения диска**: проверка свободного места поднята с
  1500 до 2600 МБ (2 ГБ под /var/swap + запас — раньше dd мог забить диск
  в ноль при 1.5–2 ГБ свободных);
* интерактивность оригинала сохранена: настройка Wi-Fi (nmcli/wpa_supplicant),
  хотспот с SSID/паролем из config.py или /etc/picarpro/hotspot.conf,
  финальный вопрос «Reboot now? (y/N)».

## MOD v1.3.0 — лимиты серво в config, анти-джиттер, MPU-клоны, мобильные тормоза

По репортам пользователя: перегрев серво (постоянные команды + дрожание),
сломанная нижняя LED-подсветка, неработающий MPU6050 («not found — will
retry in background»), сильные лаги сайта на телефоне.

* **лимиты серво — только в config.py (по ТЗ владельца)**: Steering
  30–150, Cam Pan 0–180, Cam Tilt 80–170, Crane Grip 100–180, Crane Arm
  100–180; редактирование из веб-интерфейса удалено (кнопки Edit/Save/
  Cancel, команда `servo_set_limits`, файл servo_cal.json — всё убрано);
  `servo_get_limits` остался только для отображения;
* **анти-джиттер и нагрев серво — три причины устранены**: (1) прежние
  константы клешни гнали серво В МЕХАНИЧЕСКИЙ СТОП (arm_open=80 при
  физическом минимуме ~100, grip_high=190 при максимуме ~180) — серво
  часами стояло под током и грелось; все константы теперь внутри лимитов;
  (2) повторные команды на тот же угол (keepalive джойстика каждые 150 мс)
  больше не перезаписывают PWM в PCA9685 (дедупликация в set_angle);
  (3) камерный джойстик на телефоне спамил серво-командами до 120 раз/с —
  троттлинг 25 Гц + клиентский клампинг в лимиты;
* **MPU6050 не находится — починено для клонов**: раньше чип принимался
  только при WHO_AM_I из списка (0x68/0x70/0x71/0x72), а клоны возвращают
  другие ID (0x98, 0x78...) и вечно отбрасывались с «not found — will
  retry in background»; теперь приём по ACK + успешной инициализации +
  проверке живых данных (не нули/FF); нестандартный WHO_AM_I пишется в
  лог с пометкой «вероятно клон»;
* **лаги на телефоне**: MJPEG-видео ставится на паузу при уходе со
  вкладки Control или сворачивании браузера (декодирование 15 fps JPEG —
  главный пожиратель телефона); `getBoundingClientRect` больше не
  вызывается на каждый touchmove джойстика (кэш rect на драг — был
  принудительный reflow до 120 раз/с); DOM консоли ограничен 300 строками
  (раньше рос бесконечно от фоновых логов), при неактивной вкладке
  Console строки не добавляются вовсе, история ограничена 250 строками;
  `web_active` не спамится с каждой командой move (не чаще раза в 10 с);
  на экранах <=820px отключены дорогие transition/backdrop-filter/hover;
* **Info-вкладка удалена полностью** (кнопка, разметка, JS-загрузчик
  документации);
* **DS4 Controller**: убрана SVG-картинка геймпада, оставлены кнопки
  подключения, выбор Bluetooth и расшифровка назначений кнопок;
* **LED-лента**: вывод на SPI стал устойчивее (при сбое устройство
  переоткрывается и кадр повторяется — лента больше не гаснет навсегда),
  latch-пауза увеличена до >= 50 мкс; в config.py задокументировано:
  если физическая цепочка длиннее LED_COUNT, «хвост» (нижняя лента)
  остаётся тёмным — увеличьте LED_COUNT; частая причина гашения ленты —
  просадка 5V от застрявшего в стопе серво (исправляется пунктом выше).

## MOD v1.2.1 — установщик: живой вывод, без таймаутов, диагностика импорта

По логу реальной установки: системная часть прошла идеально (apt
починился — встали bluetooth/pi-bluetooth/python3-picamera2; 13 из 14
pip-пакетов на месте), но (1) во время долгих pip-фаз консоль молчала
и было непонятно, завис установщик или работает; (2) pip дважды выходил
с кодом 0, а вывод pip в логе был пустым, при этом
`adafruit-circuitpython-busdevice` попал в «НЕ установлено» — при том,
что `adafruit_pca9685` (импортирующий busdevice внутри себя) статус
«установлено» получил. Это указывает на ложное срабатывание проверки
импорта, а не на реальное отсутствие пакета.

* **таймауты убраны совсем**: раньше установщик сам убивал команду по
  `timeout=900..3600` с (медленная установка на Pi помечалась
  «Timeout: ... skipped» и пакет молча пропускался); теперь команда
  выполняется столько, сколько нужно — прервать можно только Ctrl+C
  (дочерний процесс при этом завершается корректно, в лог пишется
  маркер прерывания);
* **живой индикатор прогресса**: перед каждой командой печатается её
  заголовок (`$ sudo -H pip3 install ...`), каждые 10 с — строка
  `... выполняется 1 мин 30 с`, для команд дольше 3 с — строка
  `готово за 2 мин 15 с`; перед pip-фазой печатается список
  недостающих пакетов и предупреждение «может занять 10-30 минут»;
* **лог пишется на диск сразу после каждой команды** (раньше весь
  журнал сбрасывался одним куском в конце — при выключении питания или
  гибели установщика терялся целиком); у каждой записи метка времени,
  при старте журнал пересоздаётся, в конце — итоговая строка с общим
  временем; зондирование apt-cache больше не засоряет ни консоль, ни
  лог;
* **проверка импорта переведена с stdout на временный файл** (главный
  фикс): результат `OK/NO` каждого модуля пишется в файл, а не печатается
  — вывод модулей при импорте (баннеры, warnings без перевода строки)
  больше не может склеиться с маркером «OK i» и дать ложное
  «НЕ установлено» — вероятная причина аномалии с busdevice в логе;
* **текст ошибки импорта в отчёте**: у провалившегося pip-пакета
  печатается сама причина (например
  `adafruit_busdevice: ModuleNotFoundError: No module named 'busio'`)
  — причина видна сразу, без чтения лога;
* при ошибке любой команды в консоль печатаются последние строки её
  вывода (не только отсылка к логу); декодирование вывода устойчиво к
  бинарному мусору (`errors='replace'` — раньше такой вывод ронял
  установщик с UnicodeDecodeError).

## MOD v1.2.0 — оптимизация CPU/RAM (под Pi 3B+ с 1 ГБ ОЗУ)

Профилирование показало, что даже в простое прошивка жгла существенную
долю CPU и ОЗУ. Главные источники: JPEG-кодирование каждого кадра при
отсутствии зрителей, активное ожидание эха HC-SR04, телеметрия 1 Гц,
50 пробуждений/с в IMU-стриме и рабочие потоки BLAS по числу ядер.

* **камера работает по требованию (главное)**: JPEG-кодирование и
  CV-обработка выполняются только при наличии потребителей — открытый
  `/video_feed`, активный CV-режим, либо зарегистрированный raw-
  потребитель (ArUco-навигация, color_scan). Без потребителей поток
  захвата спит 0.5 с (`CAMERA_IDLE_INTERVAL_S`) — экономия до 60-80%
  одного ядра в простое; открытие вкладки с видео мгновенно возвращает
  полный ритм (15 fps);
* **снижена цена каждого кадра**: `CAMERA_FPS` 30 → 15 и
  `CAMERA_JPEG_QUALITY` 75 → 60 (для web-MJPEG и CV-режимов этого
  достаточно, трафик на клиента упал ~в 2.5 раза); убрана лишняя копия
  кадра ~0.9 МБ в `submit_frame` (capture_array и так отдаёт свежий
  буфер, CV-режимы вход не мутируют);
* **HC-SR04 без busy-wait**: ожидание эха переведено на событийное
  `GPIO.wait_for_edge(timeout)` — раньше активное кручение GPIO.input
  жгло до 50% ядра при отсутствии препятствия (полный таймаут ожидания
  на каждом цикле опроса); для сред без wait_for_edge (фейки тестов)
  оставлен прежний путь;
* **телеметрия 2 Гц**: WS-броадкаст статуса и SSE-поток идут раз в
  `TELEMETRY_INTERVAL_S = 2.0` вместо 1 Гц — `get_status()` читает
  I2C/GPIO и собирает большой словарь; опрос vcgencmd (подпроцесс)
  разрежен до 3 с (`VOLTAGE_CHECK_INTERVAL_S`);
* **IMU-стрим**: без подписчика спим 0.25 с вместо 50 пробуждений/с;
  при активном подписчике точный ритм 20 Гц сохранён;
* **лимиты потоков BLAS/OMP**: systemd-юнит и boot.py задают
  `OMP/OPENBLAS/MKL/NUMEXPR_NUM_THREADS=2` — по умолчанию OpenBLAS
  создаёт рабочий поток на ядро с крупными стеками (лишняя ОЗУ и
  синхронизация); на YOLO/numpy при 4 ядрах это не влияет;
* **YOLO**: плашка «YOLO MODEL NOT FOUND» рисуется один раз, а не
  на каждом кадре (3 cvtColor + putText экономим);
* **память**: кольцевой буфер логов 2000 → 800 строк (~150 КБ);
* **WebSocket**: `compression=None` (сжатие мелких JSON дороже, чем
  выгодно), ping 30 с, очередь 4 — меньше сисколов на сообщение.

Совместимость: все команды, режимы и UI без изменений; при открытом
видео частота потока 15 fps — субъективно плавность почти та же,
нагрузка вдвое ниже. Если нужно вернуть 30 fps — `CAMERA_FPS = 30`
в config.py.

## MOD v1.1.3 — само-лечащийся установщик (по логу пользователя)

В логе реальной установки на Trixie были две ошибки: (1) apt отвергал
любую установку из-за сломанных зависимостей частичного обновления
(chromium-l10n 155 при chromium 147; libcamera 0.7.2 при 0.7.1) —
поэтому не встали bluetooth/pi-bluetooth; (2) ВСЕ pip-пакеты «не
установлено» с пустым выводом в логе — процессы pip убивались
OOM-killer'ом на 1 ГБ ОЗУ (буфер вывода терялся вместе с процессом).
Взятые из старого stage-установщика репозитория идеи (swap до pip,
apt upgrade, python3-opencv из apt) встроены в тихий установщик:

* **авто-починка apt ДО установки**: проба `apt-get -s install` ->
  `dpkg --configure -a` -> `apt --fix-broken install` -> (если не
  помогло) `apt full-upgrade -y -o Dpkg::Options::=--force-confold`;
* **swap 2 ГБ до pip**: если ОЗУ+swap < 2 ГБ, установщик сам вызывает
  `tools/setup_swap.sh` (dphys-swapfile + swappiness) — раньше это был
  ручной шаг, о котором легко забыть; именно без него pip гиб от OOM;
* **apt-first для тяжёлых пакетов**: numpy/opencv/pillow/flask/
  websockets/loguru/smbus2/evdev/spidev ставятся из apt (пред собранные,
  без компиляции на 1 ГБ); отсутствующие в репозитории (python3-luma-oled,
  python3-rpi.gpio вне RPi-репо) отсеиваются `apt-cache show` и идут в pip;
* **pip с фолбэком**: батч `--prefer-binary` + поштучная доборка — один
  кривой пакет больше не топит остальные;
* **статус по импорту модуля**, а не по pip list (apt-пакеты вроде
  python3-opencv в pip list не видны — раньше это давало ложные
  «НЕ установлено»); для opencv дополнительно проверяется `>=4.7` —
  на bookworm/bullseye apt-версия старее, тогда берётся из pip;
* **диагностируемость**: PYTHONUNBUFFERED=1 у всех дочерних процессов
  (вывод не теряется даже при гибели процесса), в лог пишется
  `--- exit: N ---` и маркеры таймаута/Ctrl+C; при неудаче в консоль
  печатаются последние строки лога;
* `dphys-swapfile` добавлен в список apt-пакетов (нужен для swap);
  DEBIAN_FRONTEND=noninteractive — apt не задаёт вопросов.

## MOD v1.1.2 — тихий установщик: «установлено / НЕ установлено»

По запросу: установщик больше не заливает консоль выводом apt/pip
(на сломанном apt это были сотни строк повторов).

* весь вывод всех команд (apt update/install, pip, raspi-config,
  systemctl) захватывается и пишется в `/tmp/picarpro-setup.log`;
* в консоли по каждому пакету печатается ровно одна строка статуса:
  `имя    установлено` / `имя    НЕ установлено` — отдельно для
  apt-пакетов и для pip-зависимостей из requirements.txt;
* статус определяется не по коду возврата apt, а по факту:
  `dpkg-query` для apt-пакетов, `pip3 list` для Python-пакетов;
* если apt-пакеты не установились, установщик печатает готовую команду
  лечения системы частичного обновления:
  `sudo apt update && sudo apt full-upgrade -y && sudo apt --fix-broken install -y`;
* `picamera2` на Debian 12+ теперь ВСЕГДА исключается из pip-списка
  (раньше — только при успешной apt-установке): если apt сломан,
  pip-установка остальных пакетов больше не срывается из-за неё;
* при неудаче pip-зависимостей установщик завершается с ошибкой ДО
  установки сервисов — чтобы не включать автозапуск прошивки, которая
  заведомо не стартанёт.

* синхронизация углов из статуса (servo_angles) с защитой от перезаписи
  поля в фокусе.

## 2. Безопасность

1. **MAC-инъекция в bluetoothctl** (`routes/bluetooth.py`): MAC из запроса
   уходил в stdin bluetoothctl без валидации — перевод строки в MAC позволял
   внедрить произвольные команды (`remove *`, `quit`). Добавлена строгая
   валидация `^([0-9A-Fa-f]{2}:){5}[0-9A-Fa-f]{2}$` (`validate_mac`), все
   точки входа проверяют формат.
2. **CORS `*`** (`web/app.py`): wildcard CORS удалён. Белый список задаётся
   `PICARPRO_CORS` (по умолчанию CORS полностью выключен — UI одностраничный
   и same-origin).
3. **Опциональная токен-авторизация** (`web/auth.py`): при заданном
   `PICARPRO_TOKEN` все `/api/*` и `/cmd/*` и WebSocket требуют токен
   (заголовок `X-Auth-Token`, `?token=`, либо первое WS-сообщение
   `{"cmd":"auth"}`). Сравнение через `hmac.compare_digest` (timing-safe).
4. **SECRET_KEY** больше не константа `'picarpro'`: из окружения либо
   автогенерация `secrets.token_hex(32)` с сохранением в
   `instance/secret_key` (chmod 600).
5. **Заголовки безопасности**: `X-Content-Type-Options`, `X-Frame-Options:
   DENY`, `Referrer-Policy`, CSP без inline-скриптов.
6. **`MAX_CONTENT_LENGTH`** = 1 MiB на запрос.
7. **Path traversal** в `/docs/components/<fn>` — блокировка `..`.
8. **Утечка стека** в WS-ответах об ошибках обрезана до 200 символов.
9. Из унаследованных уязвимостей оригиналов НЕ перенесены: логин
   `admin:123456` по открытому WS, пароль точки доступа `12345678` как
   единственная защита, APPServer без аутентификации, `os.system` с
   конкатенацией, захардкоженный ключ DeepSeek в Examples v2
   (`sk-cb36...` — ключ отозван не был, упомянут в README).

## 3. Ошибки памяти / ресурсов

1. **Голосовой запуск сломан полностью** (`functions/voice_command.py:57-63`
   в jsck37): дескриптор `open(...)` открывался в `with`-блоке и ЗАКРЫВАЛСЯ
   до `Popen(stdout=f)` — Popen получал закрытый файл, голосовое управление
   никогда не стартовало. Фикс: дескриптор хранится в `self._sherpa_log`,
   закрывается в `_stop_sherpa`.
2. **Subprocess-шторм IP** (`network.py`): `get_ip()` вызывал до 4
   subprocess `ip addr show` на каждый тик статуса (раз в секунду на
   каждого клиента). Добавлен кэш на 30 с (`reset_ip_cache` для тестов).
3. **Sleep в обработчике запроса** (`utils/system_info.py`):
   `get_cpu_usage()` спал 0.3 с внутри каждого запроса статуса. CPU/RAM
   теперь собирает фоновый поток-сэмплер с кэшем (2 с), ответы отдаются
   мгновенно.
4. **Утечка потоков сглаживания крана** (`hardware/ds4.py`): каждое нажатие
   кнопки порождало новый поток `_smooth_crane`. Частые нажатия = dozens
   threads. Теперь цель хранится в `_smooth_targets` — активный поток
   подхватывает новую цель, новые потоки не создаются.
5. **Гонка set()+clear()** (`camera/camera_opencv.py`):
   `_frame_ready.set(); _frame_ready.clear()` подряд — ожидающий поток мог
   никогда не проснуться (кадры «зависали»). Событие теперь остаётся
   установленным до следующего кадра.
6. **Пересоздание I2C/PCA9685** из оригиналов (RPIservo.py:63-69 v1/v2 —
   новый объект на каждое движение сервы) в jsck37-архитектуре уже было
   исправлено (один контроллер с локом) — поведение сохранено и покрыто
   тестами.
7. **video_feed без камеры** возвращал вечный пустой MJPEG-поток — теперь
   честный `503 Camera not available`.
8. **ADS7830-монитор** проверяет наличие АЦП на шине до создания ридера —
   без АЦП не держит открытый SMBus.

3. **Неизвестные команды** теперь возвращают явную ошибку

   (`Ultrasonic sensor not available` и т.п.) вместо `ok:false` без причин.

## 9. Установка

Без изменений по духу jsck37, но с двумя сервисами:

```bash
sudo python3 setup.py        # deps + picarpro.service + picarpro-hotspot.service
sudo systemctl start picarpro
```

Переменные окружения (опционально): `PICARPRO_TOKEN` (включить авторизацию),
`PICARPRO_SECRET_KEY`, `PICARPRO_CORS` (белый список через запятую).
